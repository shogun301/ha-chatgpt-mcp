# Wyze Sprinkler capability matrix

This document records the public, sanitized capability contract for the Wyze Sprinkler extension. It distinguishes what Wyze documents for its native app, what the installed `ha-wyzeapi` / `wyzeapy` stack can actually retrieve or command, and what Home Assistant and the MCP expose. It contains no controller identifiers, zone names, network identifiers, account data, schedule identifiers, or captured timestamps.

## Evidence and state labels

Every state returned by the MCP is labeled with one of these evidence classes:

- `commanded`: a command the MCP or Home Assistant submitted; receipt does not prove that a valve physically opened.
- `controller-reported`: state returned by Wyze's controller/cloud sprinkler payloads.
- `calculated`: a deterministic value derived from controller-reported fields, such as remaining seconds from an end timestamp.
- `inferred`: a best-effort interpretation of incomplete native or recorder evidence, such as an interrupted interval reconstructed from gaps.
- `physically-measured`: a direct sensor measurement. No confirmed upstream payload currently supplies physical valve-open, measured flow, electrical-load/current, or physical water-delivery feedback.

The history-specific `evidence_type` values are `controller-reported`, `reconstructed`, and `physical`. `physical` is reserved for a future upstream physical sensor and is not emitted for the presently confirmed data.

## History contract and limits

The rolling-history response is designed for a 48-hour Gantt chart. It emits one interval per zone and includes the required keys, using `null` plus a false support flag where the upstream record lacks the requested signal. Support booleans distinguish an explicit value from the placeholder `unknown`. Actual `ended_at` comes only from an actual upstream end timestamp. Actual duration comes only from an explicit actual-duration field or is calculated from explicit actual start and actual end; commanded/planned duration is never used to fill either actual field. Interruption inferred from an unambiguous terminal outcome is labeled `inferred`. Missing outcome remains unsupported and unknown rather than being derived from elapsed timestamps. Naive local timestamp text without a UTC offset is not guessed: affected intervals are omitted and included in `omitted_ambiguous_timestamp_count`.

Native `schedule_runs` is a private, undocumented endpoint with a numeric `limit`. No cursor, page token, or account-lifetime enumeration has been confirmed in `wyzeapy`, captured examples, or the corroborating JavaScript client. Therefore “full watering history” means only a bounded union for the requested 48-hour window: recent native records plus locally retained Home Assistant recorder snapshots. The response reports native/recorder input and interval counts, deduplication count, `upstream_complete: false`, and a limitation string. It does not claim that those counts establish native truncation, recorder coverage duration, or completeness of the window.

## Unsupported-result contract

The read capability response enumerates unsupported signals and operations with machine-readable `supported: false`, a concise human-readable reason, and upstream evidence or limitation text. It does not currently define stable machine-readable reason codes. This is used for:

- account-lifetime history pagination;
- schedule create, update, delete, enable, disable, and manual-program run;
- a dedicated, complete upcoming-run feed;
- raw Wyze weather/location inputs and Sprinkler Plus intermediate decisions;
- a distinct manual-skip command;
- live wired-sensor contact state when the payload supplies only configuration;
- physical valve position, measured water flow, electrical load/current, and hardware fault codes.

The existence of an undocumented route is not enough to enable a mutation. Schedule POST/DELETE operations remain disabled until exact request bodies, identifiers, concurrency behavior, and responses are independently captured and verified without risking a live schedule.

## Provenance and stability

Wyze's public API-key documentation describes authentication but does not publish a sprinkler API contract. Wyze's public support pages document native-app behavior, not wire formats. The integration therefore uses Wyze's existing Home Assistant credential storage and private cloud routes already used by `ha-wyzeapi` / `wyzeapy`; it does not add a second credential store.

The private irrigation API can change without notice. Reads return capability and endpoint-health metadata so callers can handle loss of a field explicitly. The normalizers return only allowlisted known fields; unknown values inside allowlisted enum-like string fields are retained rather than silently remapped. Arbitrary unknown payload fields are discarded. Commands stay on the narrow, already-confirmed Quick Run and STOP request shapes. No command is executed in automated tests or production acceptance.

## Upstream attribution and license boundary

The Home Assistant overlay contains files derived from `SecKatie/ha-wyzeapi`, whose reviewed upstream source is licensed under Apache License 2.0. The source distribution includes the complete upstream license as `home_assistant/wyzeapi_overlay/UPSTREAM_LICENSE` and an attribution/modification notice as `home_assistant/wyzeapi_overlay/NOTICE`; modified source files carry SPDX and modification notices where their format permits comments. Those attribution assets must remain with redistributed overlay source. The guarded deployment copies only the runtime custom-component files into Home Assistant, while the repository retains the attribution assets as source-distribution evidence. See [H2].
